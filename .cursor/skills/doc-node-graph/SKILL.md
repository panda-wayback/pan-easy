# Doc Node Graph

服从仓库 always-apply「方案先行」。本 Skill 只规定 **docs 怎么写、怎么推进**（所有项目统一用 `docs/`）。

## 门禁

写/改 `docs/**` 前：

```text
Agent 给出最佳方案草案 → 用户裁定合理 → 只写入已裁定且合理的内容
```

禁止：未探讨/未裁定入档；探讨稿入档；不合理内容入档；**未裁定自行写入或实现**。  
例外：纯机械同步（状态行、推进句与现状对齐、断链修复）可直接改。

不合理 → 指出并坚持合理做法；禁止迎合。  
默认可只给最佳方案；仅当无清晰唯一最优时，才用 ≤3 条一行对比并标 **推荐**（禁止无推荐的选项菜单）。

## 节点结构

能力节点标题顺序：`目标` → `要实现的` → `解决步骤`（`状态` 可选）。

| 标题 | 写什么 |
|---|---|
| 目标 | 是什么、做成什么样 |
| 要实现的 | 谁/场景/能做什么；关键约束与失败 |
| 解决步骤 | 已裁定大步骤；须能看出做得到；候选须标未选定；子链接与顺序 |

- 需求优先；短句/列表；禁止伪代码、代码说明书、在正文教写法。
- 未裁定的解决步骤保持「待拆」。
- 点名依赖时覆盖需求涉及的参与方；禁止只写一层。
- 禁止写：调用方身份、上下级实现细节、函数级步骤、配置键、部署命令。

非能力页：只写 `目标`、`解决步骤`。

## 算法（裁定后才写）

```text
写目标 + 要实现的
写解决步骤
  ├─ 未裁定 → 不改解决步骤；给判断；禁止建子目录
  ├─ 已裁定且本页可写完 → 写入本页
  ├─ 已裁定需子页且不存在 → 只建空架子并链接；停止
  └─ 本页写完 → 停止
更新索引（若有变更）
```

空架子：`目标` + `要实现的`（已知部分）+ `解决步骤：待拆`。禁止同轮再拆其内部。

建节点：已裁定要建，且需独立理解/调用 → 一目录一 README；否则留在父解决步骤。同一能力只建一处。禁止提前建未轮到的目录。

链接：可见文字 = 仓库根路径；对能力节点只用其目标/要实现的，禁止抄解决步骤。

## 选下一步

```text
1. 根 docs 解决步骤顺序
2. 根索引「推进」类语句若与现状冲突 → 先改索引再往下
3. 第一个未完成节点/步骤
4. 待拆/未裁定 → Agent 给最佳草案；用户裁定前不写 docs
5. 仍有未完成子链接 → 进入子节点
6. 裁定后写当前项；本轮停止
```

一轮一步。禁止同轮递归铺开。

## 补文档时判定

1. 目标/要实现的可读；关键约束与失败已写清。  
2. 解决步骤能看出做得到（或已改需求）。  
3. 所需链接页存在或空架子已有。  
4. 对所需能力只读目标+要实现的，判定需求可满足；禁止改其解决步骤（待拆除外）。

失败 → 先给判断，裁定后再补 docs。

## 变更

- 改方案/解决步骤 → 裁定 → 改 docs →（若已有代码）再改 code  
- 接口不变的实现调整 → 可直接改 code  
- 产品正文只在 `docs/`；禁止写入本 Skill  
- 保持简单；不为守规则堆文档  
- 本 Skill 保持通用；禁止写死单仓业务模块表或产品名词  

## 模板

```markdown
# <能力名>

## 目标

## 要实现的

- …

## 解决步骤

1. …
```

`docs/README.md` 可为根能力页。索引表/A→B 可选；禁止为凑索引造空表。
